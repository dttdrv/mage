# mage 0.1 alpha — design spec

Date: 2026-07-21. Status: approved by user (direction + this design).

## What 0.1 is

A zero-dependency Python 3.9+ CLI (`mage/bin/mage`) that turns the validated
research workspace into a product core: declarative per-game recipes, a
runtime registry, bottle (prefix) management, launching, and failure
diagnostics. GUI (SwiftUI) is 0.2, as a thin shell over this core.

Hard constraints (user): universal only — no per-game perf logic in code, no
machine-specific tuning; all tuning lives in recipe data. OSS only.
Stdlib only (system python3 is 3.9.6 → recipes are JSON, not TOML).

## Layout

- `mage/bin/mage` — the CLI (single file, stdlib only).
- `mage/recipes/<id>.json` — one file per title. doom2016 is the flagship.
- `mage/runtimes/<id>.json` — runtime manifest; `root` may be relative to
  the mage dir (0.1 registers the existing
  `../toolchains/wine-mage-11.13/install` by reference — no 500 MB copy).
- `mage/prefixes/<name>/` — bottles created by mage. Imported prefixes stay
  where they are; mage only drops a `.mage-bottle.json` marker inside.
- Logs: `/private/tmp/mage-<name>.log`. Diagnostics:
  `mage/docs/testing/diagnostics/<name>-<ts>.tgz`.

## Recipe schema (doom2016.json)

- `id`, `title`, `runtime` (runtime manifest id)
- `env`: exact launch environment (WINEMSYNC=1, WINEESYNC=0, WINEDEBUG=-all,
  WINEDLLOVERRIDES=mscoree=d;mshtml=d, ROSETTA_ADVERTISE_AVX=1,
  MTL_HUD_ENABLED=1)
- `file_checks`: files that must exist inside the prefix, with hint text
  (encodes the Chroma DLL lesson: `CChromaEditorLibrary.dll.bak` must exist,
  else the game spins two threads forever / AVs)
- `launch`: ordered steps `{program, args, background, then_wait}` —
  for DOOM: Steam offline in background, wait 75s, then
  `-applaunch 379720 +com_SkipIntroVideo 1 +r_renderAPI 1`

## Commands

- `mage list` — recipes + installed bottles
- `mage install <recipe> [--import-prefix PATH]` — create bottle: adopt or
  create prefix (fresh prefixes get `wineboot --init`), write marker, run
  file_checks (warnings with hints, non-fatal)
- `mage run <name> [--dry-run]` — launch steps with the runtime + recipe env
  (adds DYLD_FALLBACK_LIBRARY_PATH=<runtime>/lib). It never kills an existing
  game, Steam process, or wineserver.
  `--dry-run` prints the exact env + commands without touching anything
  (safe while a session is live)
- `mage doctor <name>` — diagnostic bundle: recipe, runtime manifest,
  resolved env, `wine --version`, sw_vers, log tail, marker → tgz

## Explicitly out of 0.1

GUI, downloading runtimes/games from the internet, winetricks, Steam
automation beyond applaunch, per-game perf toggles in code, DXVK/VKD3D
routing (no DX game is a target yet).

## Implementation plan

1. `mage/bin/mage` CLI skeleton (argparse, path resolution)
2. runtime registry + `mage/runtimes/mage-wine-11.13.json`
3. `mage/recipes/doom2016.json` (full verified env/launch/file_checks)
4. install + import-prefix + marker
5. run + dry-run (parity with `bin/doom-run.sh`)
6. doctor bundle
7. Verify: `mage list`, `mage install doom2016 --import-prefix …`,
   `mage run doom2016 --dry-run` (no live launch while the user is playing),
   `mage doctor doom2016`
